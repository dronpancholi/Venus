# Feature Lifecycle Specification

## 1. Document Overview
This specification defines the standard lifecycle stages for every feature built within our product ecosystem—from initial discovery to deprecation. It establishes clear gates, entry/exit criteria, and rollout guidelines to ensure product quality and architectural integrity.

---

## 2. Feature Lifecycle Overview
A feature transitions through 6 key phases. No phase may be skipped without VP Product authorization.

```
 [1] DISCOVERY  -->  [2] DESIGN & SPEC  -->  [3] DEVELOPMENT  -->  [4] BETA / PILOT  -->  [5] GA / ROLLOUT  -->  [6] DEPRECATION
   (Problem/Fit)       (FDR / Wireframes)       (CI/CD / QA)         (Canary Release)       (100% Rollout)         (Sunsetting)
```

---

## 3. Phase Gates: Entry & Exit Criteria

| Phase | Entry Criteria | Exit Criteria / Gates | Key Deliverables |
| :--- | :--- | :--- | :--- |
| **1. Discovery** | User feedback or strategic alignment indicates a problem. | RICE Score $\ge 500$; Idea Scorecard completed. | Problem statement; user validation data. |
| **2. Design & Spec** | Discovery exit approved. | PRD completed; Design review signed off; Dev estimation done. | PRD; Figma prototype link; Technical design doc. |
| **3. Development** | Design exit approved; Jira tickets prioritized. | Code review completed; unit tests pass; QA sign-off. | Merged PRs; passing test coverage ($\ge 80\%$). |
| **4. Beta / Pilot** | Dev exit approved; feature flag configured. | Uptime $\ge 99.9\%$; SUS Score $\ge 75$ from pilot group. | Sandbox release; feedback logs; analytics validation. |
| **5. GA Rollout** | Beta exit approved; launch plan signed off. | 100% flag rollout; no critical P0 bugs in 14 days. | Public docs; marketing assets; CS training. |
| **6. Deprecation** | WAU drops below 1% of user base; replacement is ready. | Feature codebase removed; database tables cleaned up. | Sunset notice email; migration guide; cleaned repo. |

---

## 4. Rollout & Release Ring Strategy
We deploy features gradually to mitigate risk. The standard rollout rings are defined below:

```
                      [ RING 4: 100% GA (All Users) ]
                                    |
                  [ RING 3: Beta Customers (Opt-in) ]
                                    |
                [ RING 2: Internal Dogfooding (Staff) ]
                                    |
              [ RING 1: Canary Deploy (1% Random Users) ]
```

1.  **Ring 1 (Canary):** 1% of random traffic. Monitor error logs, database CPU load, and core metrics for 48 hours.
2.  **Ring 2 (Dogfooding):** All internal company employees. Use the feature in actual work scenarios for 1 week.
3.  **Ring 3 (Beta):** Opt-in customer group (representing different ICP profiles). Run for 2 weeks to gather qualitative feedback.
4.  **Ring 4 (General Availability):** Gradual automated ramp-up: 10% $\rightarrow$ 25% $\rightarrow$ 50% $\rightarrow$ 100% over 5 days.

## 5. Deprecation & Sunsetting Policy
When a feature is identified for deprecation, the following timeline must be enforced:

*   **T-60 Days (Announcement):**
    *   Publish deprecation notice in release notes and in-app banners.
    *   Email all active users of the feature with a migration guide to the new alternative.
*   **T-30 Days (Read-Only State):**
    *   Disable the creation of new entities in the feature.
    *   Present warning modals on feature entry.
*   **T-Day (Sunset):**
    *   Turn off the feature flag.
    *   Redirect all old URLs to the new feature page or general dashboard.
*   **T+15 Days (Code Cleanup):**
    *   Engineering deletes obsolete code blocks, configurations, and database schemas.

---

## 6. Feature Health & Telemetry Metrics
Every feature must define these telemetry benchmarks before entering Ring 1:

*   **Adoption Rate:** Target % of monthly active users who perform the feature's core action $\ge 30\%$.
*   **Completion Rate:** Target completion percentage of the feature workflow $\ge 85\%$.
*   **Error Rate:** System exceptions generated by this feature must be $< 0.1\%$ of total feature calls.
*   **Latency Benchmark (p95):** Feature load and run times must be under $200\text{ms}$.
