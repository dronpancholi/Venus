# UAIEOS Part 05: Tool Engineering Manual

This manual establishes the architecture, validation schemas, sandboxing rules, and fault-tolerance patterns for tools executed by autonomous agents under the UAIEOS. Tool execution represents the primary interface where non-deterministic models interact with deterministic physical systems.

---

## 1. Dynamic Tool Loading

To keep agents lightweight, the runtime dynamically loads tool schemas, APIs, and dependencies.

```
                    [Agent Requests Tool Execution]
                                   │
                                   ▼
                   [Dynamic Tool Registry Look-up]
                                   │
                     ┌─────────────┴─────────────┐
                     ▼                           ▼
              [Local Registry]            [MCP Server Registry]
                     │                           │
                     └─────────────┬─────────────┘
                                   ▼
                   [Compile & Load Schema/Binding]
```

### 1.1 Dynamic Registry
Tools are registered inside a dynamic index. A tool record defines the execution target (e.g., local python function, remote HTTP endpoint, or MCP tool call), required environment variables, and operational rate limits.

### 1.2 Import Protocol
When an agent requests a tool execution:
1.  The runtime searches the active tool registry for the matching tool name.
2.  If the tool belongs to an inactive MCP server, the connection manager initializes the server process.
3.  The tool schema is loaded into the agent's context window as an available capability.

## 2. Schemas & Validation

All tools must declare their input schemas using standard JSON Schema (Draft-07). Strict type-checking is executed at the runtime boundary before a tool is triggered.

### 2.1 Schema Definition Pattern
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "DatabaseQueryTool",
  "type": "object",
  "properties": {
    "query": { "type": "string", "description": "SQL SELECT query to execute." },
    "timeout_ms": { "type": "integer", "minimum": 100, "maximum": 5000, "default": 2000 }
  },
  "required": ["query"]
}
```

### 2.2 Validation Gate
When an agent outputs a tool call token block:
1.  The runtime extracts the payload block.
2.  The payload is validated against the tool's JSON Schema.
3.  If validation fails, the runtime intercepts execution and returns a structured validation error payload (e.g., `{"error": "ValidationFailed", "missing_properties": ["query"]}`) to the model for self-correction. Execution never proceeds to the underlying system.

## 3. Sandboxing & Execution Safety

Executing untrusted code or system-level calls generated by neural networks requires strict process-level isolation.

### 3.1 Docker and gVisor Sandboxes
*   **Code Execution Tools:** Any tool that executes Python, JavaScript, or bash scripts must be executed inside a read-only Docker container backed by a gVisor runtime kernel.
*   **Resource Constraints:**
    *   **RAM:** Limited to $256\text{ MB}$.
    *   **CPU:** Throttled to $0.5\text{ vCPU}$.
    *   **Timeout:** Hard capped at $10\text{ seconds}$.
    *   **Network:** Blocked by default (unless explicitly whitelisted).
    *   **Storage:** Bounded to a temporary in-memory filesystem (tmpfs) that is destroyed immediately upon completion.

### 3.2 System Call Filters (seccomp)
For local tools executed directly on the host system, the runtime applies seccomp filters to block dangerous syscalls, including `fork`, `execve`, and file permission modifications (`chmod`, `chown`).

## 4. Tool Fallbacks & Circuit Breakers

To protect downstream services from cascading failures, the system applies circuit breaker patterns to all tool execution streams.

```
       ┌─────────────────────────[State: CLOSED]────────────────────────┐
       │                                                                │
       ▼ (Error Rate > 50%)                                             │ (Success Rate > 90%)
  [State: OPEN] ──► (Cooldown: 60s) ──► [State: HALF-OPEN] ─────────────┘
       ▲                                   │
       │                                   │ (Any Failure)
       └───────────────────────────────────┘
```

### 4.1 Circuit Breaker States
1.  **Closed:** The tool is healthy. Execution proceeds normally.
2.  **Open:** The tool has failed repeatedly (e.g., error rate $> 50\%$ over $10$ consecutive invocations). All executions are blocked instantly. The client is returned a fallback error, preventing network congestion.
3.  **Half-Open:** After a cooldown period (e.g., $60\text{ seconds}$), the system routes a limited fraction of traffic ($10\%$) to the tool. If those calls succeed, the circuit breaker returns to the **Closed** state. If any call fails, it reverts to **Open**.

### 4.2 Parameter Relaxation and Retries
*   **Transient Failures:** If a tool fails with a transient code (e.g., HTTP 503), the engine retries using exponential backoff:

$$t_{\text{wait}} = t_{\text{base}} \cdot 2^{\text{attempt}} + \text{jitter}$$

*   **Self-Correction Retries:** If a tool returns a data error, the agent is permitted to adjust arguments and retry up to $3\text{ times}$ before triggering a circuit break.
